# Inbox-backed Steps

`StepsLayout` sits below the desktop or mobile chat header and outside the transcript scroller. It keeps the chat mounted. `StepsAnchorBoundary` captures the outgoing viewport before a chrome update and compensates in the same commit. A reading anchor keeps its screen position; a reader at the end stays there. The fixed row height also prevents Copy feedback and next-step changes from resizing the transcript. Dropdown and phone sheet closing use the existing focus-return behavior. On Capacitor Android, the open phone sheet registers its close action with the mobile shell (`useStepsSheetBack`), so native Back closes the sheet before the shell's other layers or minimize. Removing the last eligible list closes the sheet and releases that registration.

## Authority and grouping

`smartyInbox.ts` normally reads one all-state snapshot per existing inbox badge SSE refresh. Completed and snoozed items remain in this snapshot; only open items contribute to the badge. If history fails, an open-only fallback preserves the ordinary badge and the same subscription, but never becomes a reduced Steps checklist: retained records lose actionable authority. A no-inbox 403 from the fallback clears retained records, group blockers and capabilities. Bootstrap, retry and refresh publication share one generation. A successful read publishes unless a newer read already published, so the last good snapshot stays until a newer read succeeds, and a failed newer read only revokes actionable authority. An older read never overwrites a newer published read, item receipt or other store write. Late acknowledgements cannot recount invalid history over the fallback badge or replace a newer item version. Item receipts cannot establish complete group authority. Check status revokes that authority and requests an all-state read before Steps actions return. An unchanged receipt preserves the revision and can reuse an in-flight read; a changed receipt requires a replacement read. An older full-list item cannot overwrite a newer receipt for that same recipient. There is no Steps watcher or persisted checklist. Endpoint changes and verified auth recovery clear the snapshot and reconnect the existing subscription. This includes a sidebar owner mismatch on the same origin without a login remount. The mounted ordinary Inbox also resets its list, summary, count, selection and reply draft at the runtime/auth boundary. Its late tab reads cannot restore retired content. Steps display and actions use the snapshot's captured request scope. That boundary resets list selection, open overlays, Copy feedback and pending action state without remounting the chat. Stale reads and receipts cannot publish into the replacement identity. The existing 8 MiB gateway output limit still bounds full-history availability.

`inboxSteps.ts` accepts `steps:v1:<list-id>:NN/TT`. The list ID is 1–128 ASCII letters, digits, periods, underscores or hyphens, starting with a letter or digit. Ordinals and totals are exactly two decimal digits, from 01 to 99, with ordinal no greater than total. Groups are recipient-scoped. Titles use `<topic> — <instruction>` and actions are exactly `["respond"]`. Duplicate ordinals or item IDs, inconsistent totals/topics, and malformed members poison their claimed group. The HTTP parser retains a malformed member's group identity as a blocker rather than silently dropping it. A poisoned key skips all later members. A conflict never appends another member, so each retained group holds at most its declared total, never more than 99 steps. Unrelated valid groups remain usable. A group is complete only when every ordinal exists once. New arrivals do not replace the selected list.

## Copy and completion

The whole recommendation is one raw Copy target. It is never trimmed, split, prefixed, sanitized, or given a newline. LF, CR, every C0/C1 control, Unicode format characters (including bidi/invisible Cf), and U+2028/U+2029 refuse Copy. Visual wrapping does not change the payload. The existing clipboard helper must return success before the UI says Copied. Its legacy fallback removes its temporary textarea and restores focus even on failure. Safe HTTP(S) links have a separate Open action.

Done posts the exact report in `STEP_DONE_REPORT`, `action: "respond"`, the displayed `updated`, and a fresh `opKey`. Active snoozes disable Done; a local timer updates the control at expiry without a request or watcher. Each wait is capped at 2^31−1 ms and rearmed against the real expiry, including long snoozes. Failure to prepare a secure operation key is a definite no-write refusal. Generic Inbox responses to Steps use the same guards without becoming a Done report. A tick requires the recorded recipient answer plus its matching recipient resolution, `respond` actions and timestamp. Generic resolution or Ignore is not Done. No optimistic tick is stored. An uncertain write performs one item read and never replays. Failed reconciliation requires an explicit read-only Check status before another action.

The ordinary Inbox uses the same guarded write helper and action-status hook for Steps Respond and Reopen, including one-read recovery and the Check status lock. The pending and uncertain lock lives in the shared `useStepActionStatusStore` in `inboxStepActions.ts`, keyed by runtime/auth scope, recipient and item. It survives item selection, tab changes and closing or reopening the Inbox, and the Steps row and the Inbox read the same lock. Endpoint changes and verified auth recovery clear it; an entry from a retired scope is never read. A newer item receipt takes precedence over an older tab-list response, so a successful status check cannot unlock a write against the old displayed version. Non-Steps Inbox actions keep their existing behavior.

Undo appears only when the all-state response explicitly advertises `capabilities.guardedReopen: true`. Otherwise the row explains why it is unavailable. Supported Undo posts the displayed version and a fresh operation key to reopen; no unguarded fallback exists in Steps.

Web, Electron, hosted mobile and Capacitor use the existing authenticated inbox route and shared runtime fetch. VS Code and embedded/mini chats intentionally do not mount this person-inbox UI or start a watcher; they have no existing inbox badge subscription to reuse.

Reload follows OpenChamber's existing live-edge contract; Steps does not add viewport persistence. Inbox progress, the selected native session and the draft are restored through existing seams.

Mounted tests model the real flex viewport geometry because happy-dom does not calculate layout. They prove synchronous compensation, draft/focus preservation, overlay return focus, and guarded state transitions. Main owns browser layout, reload/reconnect, native-client and real-sitting evidence. These unit tests do not claim those acceptance gates.
